Field note 02 / Web tooling

A web audit should
leave less to decode.

Page Pulse turns a URL into a compact technical report. This walkthrough explains what the service measures, how the code is organized, and where an automated check stops being a complete answer.

From a URL to a useful conversation.

A page can load successfully and still have missing metadata, confusing headings, or inaccessible imagery. Page Pulse makes a subset of those properties visible in one small report.

It is a diagnostic starting point, not a complete SEO audit, accessibility certification, security assessment, or browser-performance benchmark.

What the visitor gets.

Enter a URL. The browser requests GET /api/audit?url=…. The server fetches the target, analyzes its HTML, and returns a structured report.

HTTP status
What response did the target return?
Response time
How long did this server-side request take?
Title & description
Which metadata fields are present?
Heading structure
How many H1 elements were found?
Image-alt coverage
Which image tags have an alt attribute?
Approximate word count
How much text does the parser extract?

Report-field guide, not a live audit result. An alt attribute's presence does not establish useful alternative text.

Keep the boundaries small.

Browser client
  → GET /api/audit?url=…
  → URL validation + hostname-pattern guard
  → HTTP fetch + response checks
  → HTML analysis
  → structured report

server.js handles routes and static files. auditor.js manages the network request and checks. htmlReport.js builds the report from supplied HTML.

The health route is /health. The server supports GET and HEAD requests; unsupported methods receive a 405 response.

Two useful tradeoffs.

Separate network work from parsing

Keeping report construction separate allows parsing behavior to be tested without a live target or HTTP mocks. It also makes the source easier to explain: fetching a page and interpreting its contents are different responsibilities.

Keep target errors in the report

A target returning 404 or 500 is meaningful audit data. The API can successfully produce a report that contains an unsuccessful target status. This avoids conflating “the audit failed” with “the audited page returned an error.”

The repository includes parser-focused test cases. This walkthrough does not claim an executed test count or coverage score; duplicated test files should be consolidated before reporting those metrics.

Important limits, not fine print.

  • The SSRF defense is a basic hostname-pattern guard, not comprehensive protection. DNS resolution and redirect destinations need stronger validation before accepting arbitrary untrusted URLs.
  • Some response-size checks occur after buffering the body. Streaming limits are a better next step.
  • Regex-based HTML analysis can misread malformed or unusual markup.
  • A server-side fetch does not execute client JavaScript or measure real-user Core Web Vitals.
  • Metadata and alt-text presence checks do not judge content quality or full accessibility.

These constraints are why the project is presented as a focused learning tool rather than a production-ready multi-tenant audit service.

Explore the code or run it locally.

From a local checkout, use the repository's standard commands:

npm install
npm test
npm start

# In a second terminal:
curl http://localhost:3000/health
curl "http://localhost:3000/api/audit?url=example.com"

What to improve next

Validate resolved addresses and every redirect, enforce a streaming response limit, remove duplicated tests, and exercise the complete API boundary. Better evidence comes from those changes—not from calling the current guard complete.
