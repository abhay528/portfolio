Case study

vulnscan: finding the services you forgot you were running

A concurrent TCP scanner that fingerprints listening services, compares detected versions against a signature database, and ranks what it finds by severity — so the output is a prioritised worklist, not a wall of open ports.

Role
Sole author
Context
Thiranex internship, 2026
Language
Python 3, stdlib only
Interface
CLI · text / JSON / HTML
Status
Working, tested

The problem

The dangerous machine on a network is rarely the one someone is actively attacking. It is the one nobody remembers deploying — a forgotten staging box still answering on port 6379 with no password, or a web server running an Apache branch that stopped receiving security patches years ago.

Plenty of tools enumerate open ports. The gap I wanted to close is the step after that: an open port is not a finding. Port 8080 being open is normal. Port 8080 being open and serving an end-of-life Apache branch is a service with public exploits and no upstream fixes. A useful scanner has to close that interpretation gap itself, because the person running it at 2am should not have to.

Constraints I set

  • Standard library only. A security tool that needs a dependency tree is a tool people will not install on a locked-down host. No nmap binary, no requests.
  • Machine-readable by default. If it cannot be diffed between runs, it cannot detect drift.
  • Safe to run in CI. Meaningful exit codes, no interactive prompts.
  • Authorisation is not optional. The tool prints a legal warning on every run. Unauthorised scanning is a crime in most jurisdictions, and a scanner that stays quiet about that is teaching bad habits.

How it works

Four stages, each isolated in its own module so that any one of them can be swapped or tested independently.

1. Concurrent connect scan — scanner.py

The host is resolved once with gethostbyname, then every port is dispatched to a ThreadPoolExecutor (100 workers by default) which calls connect_ex with a per-port timeout. Results are consumed through as_completed, so a single black-holed port cannot stall the run. Closed and filtered ports return None and are discarded.

2. Fingerprinting — banner.py

Open sockets get a banner grab, and the banner is parsed into a (product, version) pair. This is the step that upgrades “port 2222 is open” into “OpenSSH 6.6.1 is listening on port 2222”, which is the difference between an inventory and an assessment.

3. Assessment — constants.py + vulndb.py

Two independent checks run against every open port. A static risk map flags services that are dangerous by design regardless of version — Telnet, exposed SMB and RDP, unauthenticated-by-default datastores like Redis, Elasticsearch and MongoDB. Separately, the signature database compares the detected version against known-vulnerable ranges loaded from JSON.

Version comparison is the part that looks trivial and is not. Versions are parsed into integer tuples and zero-padded before comparison, because string comparison gets this catastrophically wrong: "2.2.10" < "2.2.8" is True as text and false in reality. Signatures can match either a bounded range or an exact build prefix, so 6.6.1p1 normalises to (6, 6, 1) and still compares correctly.

4. Reporting — report.py

One render(result, fmt) entry point produces text, JSON, or a self-contained HTML page. Severity is an IntEnum, which means a port's overall risk is just max() over its findings, and ports can be ordered worst-first so the most dangerous result is the first thing read.

Decisions and tradeoffs

Threads, not asyncio

Scanning is dominated by waiting on connect_ex. Threads block on exactly that syscall with no event loop, no coloured functions, and no async propagating through the whole codebase.

Tradeoff: threads cost more memory per unit of concurrency, so this would not scale to a /16 sweep. For a single host across a port range it is the simpler correct choice.

Severity as an ordered IntEnum

Making severity comparable rather than a string means “worst finding on this port” is max(), sorting is free, and the CLI can derive an exit code from it.

Tradeoff: an integer scale implies findings are strictly rankable, which real risk is not — exploitability and exposure matter too.

Exit code 1 when anything is found

This is what makes the tool a CI gate rather than a thing you run manually and forget. A pipeline step can fail the build when a deploy exposes a new service.

Tradeoff: it is currently binary. Severity-threshold gating (“fail only on HIGH and above”) is the obvious next iteration.

Plain ASCII in the text report, no colour codes

The CLI can write the rendered string straight to a file with -o. Had I emitted ANSI colour, every saved report would be full of escape sequences.

Tradeoff: less pretty in an interactive terminal. Correct files beat colourful ones.

The bug I shipped

Every invocation crashed at import

cli.py called report.render(...), but report.py was never committed. The result was an ImportError on every single run, in every output format, on main.

The reason it went unnoticed is the interesting part: the test suite covered scanner.py and vulndb.py — the algorithmically interesting modules — and nothing exercised the entry point. Tests written where the logic feels hard will not catch a missing file where the logic feels easy.

I wrote the module and added a test suite for it covering all three formats, empty scans, unknown-format handling, and the escaping guarantee below. A test that imports the CLI path now fails loudly if a module goes missing again.

Hardening the reporter against its own input

Writing the HTML renderer surfaced a problem worth stating plainly: every string in that report is attacker-controlled. Service banners, product names and version numbers all come from the remote host being scanned. A host can put whatever it likes in its banner.

So a naive HTML report is a stored-XSS delivery mechanism pointed at the operator. A malicious target sets its banner to a <script> tag, the scanner faithfully writes it into the report, and the payload executes in the browser of the security engineer who opened the file — with the privileges of a local file. The scanner becomes the exploit vector.

Three mitigations, all now covered by tests:

  • Every target-supplied value is HTML-escaped on the way into the document.
  • References are only rendered as links when the scheme is http or https, so a crafted javascript: reference cannot become a clickable link.
  • Banners are collapsed to a single line before rendering. Raw CRLF in a banner would otherwise let a target forge additional report lines and fake findings that were never detected.

What this run taught me about my own design

Two details in that output are more interesting than the findings themselves, and both point at the same design flaw.

Port 2222 is labelled Unknown even though the scanner correctly identified OpenSSH 6.6.1 on it. And port 8080 produced no LOW “no transport encryption” finding, even though an equivalent service on port 80 would have.

The cause is that my static risk map is keyed by port number, not by identified service. The signature-database path is banner-driven and therefore port-agnostic — which is why it caught OpenSSH on a non-standard port. The static map is not, so anything running somewhere unusual silently skips those checks. That is exactly the configuration an attacker-facing host is most likely to have.

It is a real gap, the run exposed it, and it is the next thing I would change: key the risk map on the fingerprinted service and fall back to the port only when fingerprinting fails.

What it does not do

Stating limits precisely is part of the job — a scanner that overstates its coverage is worse than one with a narrow, known scope.

  • TCP connect scan only. No SYN or UDP scanning, both of which need raw sockets and privileges. A full connect is also noisy and lands in the target's logs.
  • Static checks are port-keyed. As above: a weak service on a non-standard port escapes the risk map, though version signatures still apply.
  • The signature database is small and hand-maintained. It is not synchronised with the NVD feed, so absence of a finding is not evidence of a patched host.
  • Banner-based fingerprinting is spoofable. A host that lies about its version will be assessed on the lie.
  • Web header findings are misattributed. When --web is used, the header findings are appended to the first open port rather than tracked against the URL they came from. It is a reporting-accuracy bug, not a detection one.

What I would build next

  • Key the static risk map on fingerprinted service rather than port number.
  • Severity-threshold exit codes, so CI can fail on HIGH but tolerate LOW.
  • A first-class target model for web findings, fixing the attribution bug above.
  • Signature ingestion from a public feed, with the hand-written entries kept as overrides.
  • Run-to-run diffing, so the tool reports what changed — which is the question an operator actually has.
